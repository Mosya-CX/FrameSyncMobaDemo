# 可定制项目测试与诊断流水线

## 目标实现

Karolina 为不同工程提供可定制的自动化测试流水线模板和调度能力，并将通用测试诊断能力作为可独立引用的第一方库交付。一个功能测试由项目适配器准备所需运行时状态、注入测试输入、采样关键数据，并按明确断言分析结果。输入不限定为鼠标/键盘：可以是 `AddBuff`、命令或领域 API；需要验证真实输入链路时，项目再接入对应输入适配器。

流水线至少记录：测试会话、场景、用例、尝试轮次、预置状态、输入、采样、断言、真实执行回执和诊断附件。Karolina展示实际测试阶段、结论、失败原因、日志完整性和 Agent 审查状态；日志和 Agent 的文字判断不能替代机器断言。事件序号在一次尝试内唯一递增；同一次尝试的多个记录器必须共用同一个身份对象。

## 技术方案

### 分层与项目适配

- Karolina 对外提供第一方 `Karolina.Testing` 程序集和 Unity Package Manager 包，作为通用测试会话合同及异步诊断的正式交付物；Unity 工程可通过 UPM 引用，其它 .NET 工程可直接引用程序集。Unity 包不依赖 Karolina 桌面宿主，也不依赖 Unity API；包通过独立程序集边界向工程提供公共类型。Unity 2022.3 的发行目标使用 .NET Standard 2.1。Karolina 桌面宿主通过项目引用同一库，不在 `Karolina.Core` 重复实现日志系统。
- Karolina.Core 负责桌面端任务编排、权限与执行闭环，不引用 Unity、帧同步类型或 Unity 生命周期；它依赖可独立交付的 `Karolina.Testing` 库。
- 项目通过可注册的适配器提供场景搭建、前置状态、输入、采样、清理与项目专属断言；项目可使用 JSON/配置模板，也可用代码实现复杂步骤。模板只描述可验证的动作和数据，不尝试自动猜测未知运行时语义。
- Karolina 的 UPM 包可从公开 Git 仓库的包子路径或发行包提供；工程无需复制 Karolina 宿主源码，也不应依赖 Karolina 桌面进程才能写测试日志。包版本升级由项目显式管理。
- Unity 适配器可以从 `Update`、`FixedUpdate`、Unity Test Framework 回调或显式事件采样。帧同步 Tick 是可选时间轴适配器；没有自有 Tick 的工程仍可使用墙上时间、单调耗时和 Unity 生命周期坐标运行完整测试。
- 时间记录包含 UTC 时间和进程内单调耗时。可选时间轴位置必须声明域，例如 `UnityFrame`、`FixedStep`、`SimulationTick`；它只用于定位和排序。只有项目明确指定的权威时钟才参与该项目的行为断言。

### 测试执行阶段

1. **准备**：装配场景/运行时对象、加载配置、设置初始状态并确认夹具可用。
2. **注入**：通过领域 API、命令、Unity 输入适配器或测试控制器施加预设刺激。
3. **采样**：按事件、生命周期回调或项目时间轴读取选定状态；默认只采集必要信号，不逐帧倾倒全量对象状态。
4. **分析**：使用项目断言和测试运行器的真实终态判断通过、失败、未执行或中断，保留逐项结果。
5. **诊断**：失败或长时间无进展时，生成更细的定向观测配置和日志，再次采集失败证据；不得放宽或删除原断言来制造通过。
6. **清理**：恢复测试独占的运行时夹具，封存本次结果与附件。

综合 PlayMode 测试采用预先编排的场景、输入计划和测试控制器/求解器；Agent 不在每帧依赖模型往返来控制游戏，也不通过抢占用户鼠标观察状态。实机测试可以异步写入本地诊断日志并在运行结束后交给 Agent 分析。

### 通用异步诊断

每条诊断事件关联 `runId`、场景/用例、尝试、来源层、事件类型、严重度、UTC 时间、单调耗时及可选时间轴坐标。`Karolina.Testing` 提供有界队列、后台 IO、显式刷新与结束封存；游戏生命周期中的生产者不得等待磁盘或网络。队列容量、丢弃数、写入失败、未刷盘和附件完整性对会话可见。日志库不要求 Karolina 桌面进程运行。会话文件默认由宿主写入连接工程的 `.karolina/state`，不写入 Karolina 自身仓库。

FrameSyncMoba 现有诊断器是一个项目适配参考：它的后台队列、批量写入、刷新、失败与丢弃计数可用于对照；`MatchId`、玩家槽位、Tick、静态上下文和构建宏不进入通用合同。通用日志核心也必须可由纯 .NET 宿主创建和关闭。

### Agent 修复与审查

自动修复默认最多 2 轮，并在统一设置中可配置且有上限。每一轮代码修改后，启动独立子 Agent 按需求、测试定义和当前差异复审；审查发现必须先处理并再次确认，随后才重跑机器验证。审查无法启动、没有真实完成回执或结论不明确时，不得记为通过。

两轮仍失败或 Agent 长时间无法定位时，停止自动生产代码修改，提升目标信号的采样频率/字段、保留前后文和调用来源，运行定向诊断，并把诊断结论和剩余问题交还用户。诊断扩展不得静默消耗额外修复轮次；只有用户允许继续后才开始新一轮修改。

### 预编排运行器与能力检索

通用库提供按项目时钟运行的条件动作序列：读取初始状态，等待动作前置条件，按声明顺序执行一次动作，连续采样，全部动作完成且结束条件满足后进入分析；达到采样上限或时限明确失败，取消后由外层流水线清理。动作执行后必须重新采样，不能使用动作前的状态判断动作成功。项目适配器负责真实生命周期/逻辑Tick、领域API和采样字段；运行器不依赖Unity、模型实时响应或鼠标。

Agent制定计划前查询项目显式注册的功能覆盖、测试入口、适配器、可注入动作和采样字段，并结合工程图谱定位尚未注册的测试源码。显式能力不代表本次通过，静态候选不代表已实现覆盖；查不到时继续读源码并在计划列出能力缺口，不凭名称编造可执行测试。

每次运行保留项目明确提供的输入、可选种子、适配器/依赖版本和时间域。没有随机性时种子为空。实际证据绑定run/scenario/attempt，断言可以定位具体样本、实际值、预期值及本轮修复复审。右侧展示测试名称、通过数量和阻塞原因，详细日志默认收起；仅保留必要信号，参数不得包含凭据和无关个人信息。

### 独立测试页面与无需计划的复现

提供与AI对话同级的“测试与验证”主页面，移除状态栏“测试复现”按钮。手动选择一个或多个测试条目即可运行，不要求新建或关联执行计划。条目包含原有准备、输入、采样、机器断言、源码路径与能力，补充模块/标签、清理、诊断及可选需求/计划关联；关联资料只用于按需查阅，不成为纯复现前置条件。允许按关联资料标题定位。

默认只运行机器测试，不显示无用途的Agent模型控件。勾选自动修复后可选择实际模型/思考挡位；沿用工程权限、默认两轮、独立复审和原检查复测。手动复现冻结所选条目而非从关联计划合并其它检查；不新建占位需求或计划。纯测试不创建待审批空任务，不扫描全工程审批基线；允许Agent修复时才保留真实修改前基线，产生Agent变更后进入任务审批。既有“执行任务”根据计划自动测试的链路继续保留。

页面展示可选场景、准备/输入/断言、启动与阻塞反馈、当前执行状态、停止、实际回执/样本/复现参数和历史运行。后台执行不得自动切换用户页面；结束记录仍可按需查阅。

## 边界情况

- 没有 Tick、Unity 未运行、夹具构造失败、输入适配器缺失、测试被取消、测试超时、日志队列溢出、输出写入失败、诊断不完整和 Agent/审查子 Agent 断连都必须留下真实状态和原因。
- 无时间轴位置时写入 `null`，不得伪造帧号或 Tick。不同时间域不可直接比较；跨进程顺序使用事件序号和 UTC/单调时间。
- 机器验证只依据执行计划或本次冻结测试条目声明的断言与真实测试回执。日志完整性不足可阻止结论为通过；日志内容本身不能让失败断言转成通过。
- 额外采样受容量与时间限制，失败后保留原始失败用例及其定义，细化测试不能替换或削弱原验收条件。
- 实机日志只收集项目明确标记的诊断信息；用户消息、密钥、访问令牌和无关个人数据不得默认写入或上传。
- Karolina 不强制安装本地模型或新增付费 API；适配器可由项目按需提供。UnityMCP 权限仍由 MCP 管理。

## 验收条件

- 制定计划按通用模板写六层测试设计，并关联真正可执行的检查；普通执行任务在实施结束后自动完成测试、独立复审和有界修复，不要求用户额外点击测试。手动测试入口仅用于复现、复测和人工验收辅助。

- `Karolina.Testing` 可作为独立程序集/UPM 包引用；纯 .NET 和 Unity 工程均可创建、写入、刷新并关闭测试会话。事件具有稳定关联字段，UTC/单调时间有效，时间轴位置可省略。
- 无 Tick 测试可以基于普通事件或 Unity 生命周期适配运行；帧同步项目可以额外带入逻辑 Tick，二者不会互相依赖。
- 测试生产者在队列满或磁盘变慢时不等待 IO；丢弃、错误、超时、停止和不完整状态均可查询。
- 一个样例用例可完成“预置状态→注入输入→采样→机器断言→封存证据”，且失败报告保留输入、采样片段和真实回执。
- 执行修复默认两轮，每轮有独立审查回执；达到上限或定位停滞后进入诊断增强，不自动偷偷执行第三轮生产修改。
- 在 FrameSyncMoba 现有 EditMode/PlayMode 测试中选取至少一个代表用例验证项目适配；不构建正式 Player、不用截图验收、不触碰三狼营地改造范围。

## 需求演进

### 2026-10-11 · 接受通用测试流水线方向

用户要求 Karolina 提供可适配不同项目的测试模板和自动化程序：通过预置运行时状态、注入功能输入、采样关键数据和断言分析测试结果；综合 PlayMode 使用预编排场景及控制器，不依赖模型每帧实时操控；实机测试采用异步日志供 Agent 分析。默认修复次数调整为 2，每轮修改后须由独立子 Agent 复审，失败两轮或定位停滞时增强诊断。进一步确认现有 FrameSyncMoba 异步日志与 Tick 有耦合：通用实现只借鉴后台有界写入机制，时序域必须可选，Unity 生命周期适配可独立工作。

### 2026-10-11 · 明确通用诊断库由 Karolina 对外提供

用户澄清 Karolina 应提供可由项目直接引用的通用异步日志程序集/外部包，而非只把能力留在 Karolina 宿主内部。技术方案更新为第一方 `Karolina.Testing` 库及 UPM 包；Unity 2022.3 使用 .NET Standard 2.1 发行目标。项目专属适配器仍归项目所有，日志库不依赖 Unity API 或桌面宿主。

### 2026-10-11 · 计划设计与普通任务自动执行相连

用户指出仅提供手动测试按钮不满足日常执行流程：制定计划应根据模板预先写出测试内容，执行时依据计划自动完成测试。接受方案为正文六层测试设计及独立 testDesign 元数据，与 verificationChecks 逐项对应；首次工程写入前冻结，允许创建尚未实现的测试文件但执行前必须存在。普通任务沿用原对话及任务基线，初次实现结束自动测试，机器直接通过也需独立实现复审；真实失败后每轮修改独立复审再重跑原检查。缺少声明、环境失败、回执未知或复审阻塞不交付审批；不适用机器测试必须记录理由。按钮定位为人工复现/复测，默认只测，不能替代程序自动调度或人工最终验收。

### 2026-10-11 · 批准预编排运行器、测试能力检索及证据呈现

本批新增通用条件动作与连续采样运行器，项目提供时钟与领域适配；Agent执行前检索既有测试能力并在计划登记缺口。配套精简右侧摘要、断言样本关联及复现条件。验收使用已有Buff功能测试和一个Gameplay PlayMode场景，沿用普通任务自动测试及默认两轮独立复审规则，不依赖额外测试按钮或模型实时操作鼠标。实际完成状态以本批证据为准，历史机器结果不替代本批联调和人工验收。


### 2026-10-12 · 测试条目独立执行与主页面

用户明确手动复现不应绑定计划，相关元信息应在测试条目中保存并按需查找；测试界面应为与AI对话同级的主页面，移除状态栏入口。接受上述独立条目与主页面方案，原计划自动执行及真实Agent修复审批继续复用现有流程。
